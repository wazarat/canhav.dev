# Markdown export and MCP

**Available now.** Both are free; a few project tools belong to [Studio+](../accounts/studio-plus.md) and say so. Exports, the `get_my_` tools and project servers need a CanHav account; public data over the shared MCP server needs none. See [Accounts](../accounts/clerk-accounts.md).

In short: there are two kinds of MCP server. The **shared server** reads every launch and every published design. A **project server** is bound to one studio project, reads that project and its token, and can write to its draft when the owner allows it. The studio hands you a ready prompt for each, so you rarely type any of this by hand. See [Connecting](#connecting).

## Markdown export

Every published Product or Token design page (`/p/[slug]` and `/t/[slug]`) has two download buttons. Sign in once and the files download directly.

| Artifact | Purpose |
|----------|---------|
| `canhav-[slug].md` | Markdown export of the published design snapshot. For a project with a product module it carries the resource pack and where the protocols run today. A token design's export takes its build step ticks from the current draft, since those change after publishing |
| `AGENTS.md` | Agent-oriented summary of the design for IDE and coding agents. A linked pair is merged: a token design's file carries its project's published snapshot, and a project's file carries its linked design's. Carries the resource pack for a project with a product module |

### Exports from a draft

A project's research happens before publishing, so its owner can export from the current draft. The Publish section of the project page offers both files once the project has a product module; the route is `/api/export/project/<project id>` and answers only to the signed-in owner, 404 to anyone else.

| Artifact | Purpose |
|----------|---------|
| `?file=resources` | `RESOURCES.md`, the ticked resource pack alone, grouped Core, Recommended and Deep dive, core items numbered in read-first order, then the build steps with their done state, the contract templates grouped Accepted, Undecided and Rejected, the review passes with their verdicts, an environment section, and "Your files", the file references you added to the project |
| `?file=onepager`, `?file=deck` | Studio+. `ONEPAGER.md` and `DECK.md` (one `##` per slide) from text written in the studio before M159, while the team keeps it. `?file=grants` is gone |
| `?file=agents` | `AGENTS.md` built from the draft plus the linked token design's draft, marked as a draft export in its first paragraph. Opens with the project's chain and includes "Your files" |

## MCP server

The CanHav MCP server runs at `https://www.canhav.com/mcp` over Streamable HTTP. Public data (published designs and every deployed launch) is readable without signing in. Tools that start with `get_my_` need an OAuth sign-in with your CanHav account, which the client prompts for on first use.

Connect from Claude Code

```bash
claude mcp add --transport http canhav https://www.canhav.com/mcp
```

Other MCP clients (Cursor, ChatGPT connectors, Claude Desktop) take the same URL. Dynamic client registration is enabled, so no manual OAuth app setup is needed.

Launches live on two chains, Robinhood Chain Testnet and Arbitrum Sepolia. You never tell a launch tool which chain: it finds the token on either chain from its address, and every token it returns carries `chain` and `chainId`. The one exception is `get_launch_governance`, which takes an optional `chain` because it describes a chain's contracts rather than a token.

These read the same launch indexer and journey tables as the launch pages, so an agent sees exactly what a visitor sees. All are read only. Nothing signs, submits, or stores.

| Tool | Purpose |

| `get_launch_journey` | The committed document with the on-chain hash, the recomputed hash and whether they match. `source` is `journey` for the quick launch form or `design` for a launch from a published design, in which case `design` names the snapshot and `milestones` carries the design's milestones |
| `get_milestone_updates` | Creator-authored progress updates whose stored body matches the anchored hash, grouped by milestone. `milestones` comes from the journey or from the committed design snapshot |
| `get_sale_status` | Allocation sales with phase (upcoming, open, closed, reclaimed), amounts, proceeds tranches, and recent purchases |
| `get_pool_status` | The launch's AMM pool with reserves, fees, swap count, volume, and recent swaps. For a curve launch this is the pool the launcher seeded at graduation, flagged `lockedLiquidity` |
| `get_curve_status` | The bonding curve behind a launch made through the curve launcher. Every launch tool returns an error result with a retry hint when the indexer is unreachable, and a validation error for a malformed address.

## Project keys

**Studio+.** A project can mint keys (project page, Deployments, Project keys) that stand in for the OAuth sign in on that project's server and on its draft export, for cloud agents and CI. A key is `chk_` followed by random characters, shown once; CanHav keeps only a fingerprint. It speaks for the account that made it and for the project's team, so revoke it when someone leaves.

| Scope | Opens |
|-------|-------|
| read | Every read tool of the project server and the draft export (`/api/export/project/<id>`, `?file=agents`, `?file=resources`) |
| write | The read tools and the write tools, under the project's agent write mode like any agent |

Send it as a bearer. For Claude Code, `claude mcp add --transport http <name> https://www.canhav.com/mcp/p/<id> --header "Authorization: Bearer chk_..."`. A key used on another project's server reads as not yours; a read key answers a write tool with a note to use a write key. The shared server ignores keys.

## Connecting

You do not have to assemble commands yourself. The site gives you one prompt to paste into Claude Code, the Claude desktop app or another AI IDE that speaks MCP. The prompt tells the agent to add the server, sign in where needed, read, and report back.

### The launch prompt

It adds the shared server, reads the launch by address (curve, pool, sales, and the commitment when there is one) and reports where the token stands. When the launch is linked to one of your projects, the same prompt also adds that project's server and reads the project.

| Where | What you see |
|-------|--------------|
| Launch success screen | The prompt in a copy block, right after launching |
| Studio, Launches list | An **Agent prompt** button on each launch row |
| Token page | An **Agent prompt** button across from the name, for the account the launch is recorded to. Other visitors do not see it |
| Studio, project page | An **Agent prompt** button beside each launch in the Token launch panel on Overview |

Reading a launch needs no sign-in. The prompt only asks you to authenticate if you want your own launches through `get_my_launches`.

A launch is linked to a project on the launch form or afterwards in the studio, where the link can be changed or removed, including by pasting the token's address, its short form or its page link into the Token launch panel. See [Projects and launches](../token-launch/projects-and-launches.md). An agent on the project's server does the same with `link_launch` and `unlink_launch`.

### The project prompt

Open a project in the studio. The **Agent prompt** button across from the project's name opens the guide for that project's server, and the connect block on Overview carries the add command and the prompt. It leads with one prompt to paste, and its last step follows the write mode you pick at the top of the guide. Under "Read the steps yourself" the guide also has every step by hand: the add command, signing in with `/mcp`, checking with `claude mcp list`, example prompts, the server address for other apps, troubleshooting and the command to remove the server.

## Project-scoped servers

Every project in the studio also has its own MCP server at `https://www.canhav.com/mcp/p/<project id>`. Its tools are bound to that one project, so none of them takes a slug or an address. The guide described under [Connecting](#connecting) gives you the prompt and the exact command. The server is named after the project so several can be added side by side: `canhav-` plus the project name in lowercase with dashes (up to 24 characters), or `canhav-` plus the first eight characters of the project id while the project has no name.

```bash
claude mcp add --transport http canhav-<project> https://www.canhav.com/mcp/p/<project id>
```

Permission prompts. Claude Code asks before the first use of each tool in a session, and a scoped server has around twenty-five, so a run that reads the status, the pack, the steps and the templates and then writes meets many prompts. "Yes, and don't ask again" writes one rule per tool to `.claude/settings.local.json`. The project guide has a block to paste once into `.claude/settings.json` in the repository: `permissions.allow` with `mcp__<server>__get_*`, `mcp__<server>__check_*`, `mcp__<server>__set_*`, `mcp__<server>__update_*`, `mcp__<server>__add_*`, `mcp__<server>__create_*`, `mcp__<server>__report_*`, `mcp__<server>__withdraw_*`, `mcp__<server>__link_*` and `mcp__<server>__unlink_*` (tool name wildcards are honoured, server name wildcards are not). Pre-approving the write tools is safe because the project's write mode, propose by default, decides what reaches the draft. Every tool also carries MCP annotations (`readOnlyHint` on the read tools, `destructiveHint: false` everywhere) for clients that use them; Cursor has its own auto-run setting for MCP tools.

Unlike the shared server, a scoped server is owner-only and requires OAuth on every request. The first call returns 401 with a `WWW-Authenticate` header, which is what makes the client open the browser flow. The browser flow goes through the studio sign-in page: Clerk sends the visitor to `/studio?redirect_url=` with the consent screen on the Account Portal as the target, the sign-in card follows it after a sign-in, and a signed-in account is sent on by the page itself.

The token tools answer with an error until a token is linked to the project, by a launch or through its deployed linked design. The design tools answer with an error until a design is linked, which the agent can do itself with `create_linked_token_design`. Their names match the shared server's on purpose, so a prompt written for `canhav` reads the same on `canhav-<project>`; Claude Code keeps the two apart by server name.

The scoped server also registers one prompt, `prelaunch_review`. In Claude Code it appears as a slash command named after the server; it walks the passes against the open repository and reports a verdict with evidence for each. Clients that do not surface prompts get the same content through `get_prelaunch_review`.

### Writing to a draft

An agent on a project's server can change that project's draft, tick build steps, and change the linked token design's draft. The owner decides how, either at the top of the project's agent guide or on the project page under Overview. A proposal is accepted or rejected whole there (Accept all, Reject all), with the draft's current value shown beside the agent's for each line. `get_agent_changes` shows what reached the draft as `appliedPatch` beside the original `patch`.

| Mode | What happens to a change |
|------|--------------------------|
| Propose changes | It waits in the studio. The draft is unchanged until the owner accepts it. This is the default. Every read on the server returns the projected state, the draft with the waiting proposals applied oldest first, so the agent can build on its own proposals in one run. |
| Write directly | It lands in the draft at once and is listed in the studio. |
| Off | The agent reads only. Write tools return an error that says so. |

|------|--------------|
| `update_project` | Change fields of the project draft. Every write tool takes an optional `note` for the owner and answers with `outcome`, either `proposed` or `applied`, plus `pending` (how many proposals wait, their ids and the review URL) and, for a project with a product module, `projectedProgress`, the build progress once the waiting proposals are accepted.

Projected state. In propose mode every read tool on a project server (`get_project`, `get_project_status`, `get_build_steps`, `get_templates`, `get_resource_pack`, `check_project`, `check_design`, the design and token step reads and the `prelaunch_review` prompt) answers with `source: "projected"` and the drafts as they become once the owner accepts what is waiting, applied oldest first, and a `pending` block with `count`, `changeIds` (the proposals the projection applied), `skipped` (waiting proposals that no longer apply, with the reason) and `reviewUrl`. Pass `preview: false` to read the stored draft (`source: "draft"`). In direct and off modes nothing waits, so both read the same. Proposals are checked against the projected drafts, so an agent can propose a product module, then build steps for it, then a design, in one run; the studio marks a proposal that depends on earlier ones and the owner accepts in order.

Input that breaks a rule is refused with the field and the number that broke it, for example `changes.architecture.contracts is 812 characters, max 800. Nothing was changed.` Up to three problems are named per call. The same wording appears in the studio when a proposal cannot be accepted. The limits themselves are the editor's (`PROJECT_LIMITS` and `TOKEN_DESIGN_LIMITS` in `lib/ideation.ts`, `KIT_LIMITS` in `lib/kits.ts`); a note is at most 400 characters.

The paste prompt and the kit SKILL files ask the agent to tick each build step with `set_build_steps` as soon as it is done, with a note naming the file, and to record architecture facts as it learns them rather than at the end of a run. The owner sees each arrival as a notice at the bottom right of the open project page, and the studio home marks a project row with the number of proposals waiting and the date of the newest direct write.

Agent sessions. After Linear's agent sessions, an agent reports what it is doing with `report_session`: a plan before it starts, the plan updated after each step, `awaiting_input` with a message when it needs the owner, and `done` or `error` at the end. The project page shows the live session on Overview (state, title, message, the plan as a checklist, when it last reported, the link), and the header line reads Agent working or Waiting on you; the notice at the bottom right fires when the agent waits on the owner or finishes, and the studio row reads Agent working, Waiting on you or Agent error. A working session that stops reporting reads as stale after thirty minutes; the next report revives it. The paste prompt, the build steps prompt and every kit SKILL file ask for it.

What an agent cannot do. Publish or unpublish. Tick the distribution acknowledgement. Unlink a token design (it can start one for a project that has none, and it can link or unlink a launch the account owns). Change the chain of a project that already has a token. These stay with a person in the studio.

If an agent writes while the project page is open, the page takes the new draft when nothing is unsaved. If there is unsaved typing, saving pauses and the page asks for a reload, so neither side overwrites the other without anyone seeing it.

### Resource pack fields

`get_resource_pack` and `get_resource_catalog` share one vocabulary. A project is in one or more sectors; `sector` stays as the first of them for older readers and `sectors` lists all of them. A research kit opens for each sector that has one (`credit` for Credit, `liquidity` for Liquidity) once a subsector of that sector is chosen; `kit` is the first and `kits` lists all of them, and a catalog entry that belongs to one kit's own files carries `kits`. A product module can be reached from subsectors of different sectors (Curated vault and Earn inside your app from both Lending and Vaults) and carries the same resources, build steps and review passes either way, minus the other kit's own files. `family` is one of `shared`, `robinhood`, `arbitrum`, `morpho`, `pendle`, `uniswap`, `boros`. `priority` is `core`, `recommended` or `deep_dive`. `steps` names the editor steps a resource informs, `basics`, `architecture`, `security`, `reality`, `review`. `flags` is always an array and may contain `unofficial` (a community artifact to verify before trusting), `mainnet_only` (no testnet deployment exists), `not_on_robinhood` (background reading, the protocol does not run on this chain), `testnet_only` and `self_deploy` (the protocol has no deployment on testnet 46630, so the team deploys these contracts itself and records them in its own manifest). A project may build several modules at once. `shape` and `shapeLabel` stay as the first of them for older readers; `shapes` and `shapeLabels` list all of them in table order, and the resources, environment families, build steps and review passes are the union across them, each once. `environment.families` lists, for Robinhood Chain and each protocol family the modules rely on, the testnet 46630 and mainnet 4663 status (`official`, `community`, `manifest_only`, `none`), a note, a source and the recommended development path. On Robinhood Chain rows exist for `robinhood`, `morpho`, `pendle`, `uniswap` and `boros` (an Arbitrum Sepolia project gets an `arbitrum` row in place of `robinhood`), each with its own `devPath` (Uniswap's starts with a self-deploy on testnet); a module plan never includes `boros`, which runs on Arbitrum, but `get_resource_catalog` lists every row. A project builds on one chain, `robinhood_testnet` or `arbitrum_sepolia`. `get_resource_pack` carries `chain` (key, name and the testnet and mainnet chain ids) and `shapesMissingTestnet`, the chosen modules whose protocol has no deployment on that testnet with the missing families; the environment rows, the chain family (`robinhood` or `arbitrum`) and the flags follow the chain. The catalog carries `chains`, one entry per chain with its environment rows and `shapesMissingTestnet`, and `runsOnTestnetByChain` per module; `runsOnTestnet` and the top level `environments` describe Robinhood Chain for older readers. Nothing is blocked. `testnetGate.blockedShapes` stays as an empty list, and a module whose protocol is missing can be picked, with build steps the team or its agent writes through `set_build_steps`. A catalog entry written for one chain carries `chains`. Every token view carries `chain` beside `chainId`, the chain the token lives on. `checklist` carries the build steps. `done` and `total` count a step shared between modules once. `items` stays one entry per id (134 across the thirteen modules) with the step it informs, the resource ids that help, whether the team has ticked it, its `shape` and `sharedWith`, the other ids of the same work. `groups` is what the studio shows, one entry per step in section order with its `shape`, the `shapes` it serves, its `step` and `milestone` (the Build tab's grouping, `design`, `testnet`, `review` or `launch`), its `ids` and whether every id is ticked; eleven steps are shared (the review passes across every module, the fork and staging plan across the Pendle modules, and the markets, roles, testnet deployment, dead deposit and scenario walks across the vault modules). `review` carries the passes for the module with a progress block (`pass`, `fail`, `na`, `open`, `total`) and, per pass, the detail, the defining resources with URLs and the verdict or `null`. `features` (M64) carries `on`, `total` and `items`, every feature of the modules with `on`, the step ids it gates and the template ids it suggests; a template item's `suggestedBy` names the ticked features that suggest it, and `checklist.groups[].feature` names the feature that gates a step. `ideas` carries what the team could build with each module, every catalog example with `on` and the team's own lines with `own` (and `from` when the line was edited from a catalog example, which is then left out), and `count`. `templateGaps` lists the modules with no contract template live on this chain's mainnet, each with `liveOnOther` (how many run on the other mainnet) and a `plan` line (accept those and iterate for this chain, or move the project to the other chain). `templates` (M63) carries, for a project with a module, `counts` (`accepted`, `rejected`, `open`, `total`) and `items`, every active contract template placed under the modules' subsectors with its `decision`, `availability` and `onChain` for the project's chain, and `steps`, the build step group keys that list it; `checklist.groups[].templates` names the template ids per step. `launchTarget` (M69) carries, when the linked token design has chosen a venue, its `target`, `label`, `fit` for the project's chain, a `note` and `ponsFitTemplates`. Fields are only ever added, never renamed.

Two notes on what the URL is and is not. Clerk issues access tokens for the origin rather than for a path, so a token minted at `/mcp` is accepted at `/mcp/p/<id>` as well. The scoped URL is a tool surface, not a secret and not a capability: ownership is checked on every call against the signed-in account. And because the URL keys on the project id rather than its slug, a brand-new draft is connectable before it is ever published.

### Shared across sectors

The Morpho family serves both sectors. A curated vault or an earn feature reached through Liquidity carries the same Morpho, shared and Robinhood Chain entries as one reached through Credit, and the two liquidity vault modules, Liquidity allocator and Permissioned vault, reuse the earn skills, the SDK and API pages, the whole Vault V2 group, the public allocator, the risk, audit and address pages and the community testnet fixture. Where the liquidity side diverges it is in vault operations rather than protocol integration: the dead deposit, gates, emergency procedures, unwind, permissioned token integration, bundles and the lender's view of liquidation, plus ERC-8056 for tokenised stock balances and the Safe documentation for the keys behind every role. The Pendle family stays with Credit and the Uniswap family stays with Liquidity, where it serves the three pool modules with the protocol's agent skills, the docs index for agents, the contracts monorepo and the canonical Robinhood Chain 4663 record (mainnet only), the v2 pair and router, the v4 singleton with its position manager, quoter, state view, hooks, dynamic fees and custom accounting, the hook template and the public hook implementations, the Universal Router and Permit2, and the v4 subgraph. Contracts a team deploys on testnet 46630 itself carry `self_deploy`. `get_resource_catalog` shows the overlap directly: each entry lists its `shapes` and each module its `sectors`.
